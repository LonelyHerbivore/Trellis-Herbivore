# Codex 工作流无缝迁移设计

## 边界

迁移按阶段增量交付。每一阶段只能修改其 PRD 中声明的产品层、模板层或测试层；阶段之间通过 task record、中文交接记录和 Git 提交衔接。平台无关的状态和规则优先落在 `.trellis/`、Core 或共享模板，Claude/Codex 差异只留在薄适配层。

## 协作与工作目录

本父任务复用当前 checkout：`D:\Trellis\Trellis-0.6.0-beta.17`。协调会话不直接承担产品实现，负责将每个阶段派给有明确文件边界的执行 agent，并收敛其测试与 review 证据。任一后续实现任务必须从 task record 读取其已记录的实际 worktree；不得自行再创建第二个工作目录。

## 阶段依赖

- 阶段 0 是所有后续任务的前置条件。
- 阶段 1 的 task 状态契约是阶段 5 和阶段 6 的前置条件。
- 阶段 2 的共享入口契约是阶段 3、4 和 7 的前置条件。
- 阶段 3、4、5、6 可以在各自依赖满足后拆分调研，但集成顺序固定为 1 -> 2 -> 3 -> 4 -> 5 -> 6 -> 7 -> 8 -> 9。
- 阶段 8 只验证已完成的打包资产；阶段 9 不引入新产品能力。

## 兼容与停止条件

- 旧 task、旧 `.claude/worktree`、用户自定义入口和其他工具共享的 `.agents/skills` 必须保留兼容。
- 如新状态字段、workflow 文案和 agent prompt 对同一合同解释不一致，停止后续实施并回到阶段 1 或 2。
- 如任何变更可能覆盖用户入口、agent、skill、运行时数据或用户级 Codex 配置，先增加保护测试并在用户配置写入前获取明确授权。
- tarball 缺失运行时资源、同一任务出现两个实际 worktree、或 clean-install E2E 仍依赖开发机绝对路径，均视为发布阻塞。
